# ADR-0009 — Pinned CI/CD Dependencies for Enterprise Stability

**Status:** Accepted
**Date:** 2026-08-12
**Deciders:** Manus (author), RISKX spec §24 (error handling), security posture

## Context

RISKX targets enterprise consumers, for whom CI/CD supply-chain stability is a first-class requirement. Floating or major-version-only CI references (`@v1` drift, unpinned linters) expose builds to upstream breakage and, in the worst case, to compromised upstream repositories (a known class of supply-chain attacks). At the same time, linter and toolchain versions must be verifiable against their upstream sources — not taken from memory.

## Decision

Provide four GitHub Actions workflows, each with pinned, upstream-verified versions:

| Workflow | Purpose | Pinned versions (verified 2026-08-12) |
| --- | --- | --- |
| `.github/workflows/ci.yml` | Build and full test suite | `actions/setup-go@v7`, `actions/checkout@v4`-class equivalents per upstream |
| `.github/workflows/lint.yml` | golangci-lint | `golangci/golangci-lint-action@v9`, linter binary **v2.1.6** (enabled linters: `errcheck`, `govet`, `ineffassign`, `staticcheck`, `unparam`, `unused`, `whitespace`) |
| `.github/workflows/staticcheck.yml` | honnef staticcheck | `dominikh/staticcheck-action@v1` |
| `.github/workflows/vuln.yml` | dependency vulnerability scan | `golang/govulncheck-action@v1` |

Rules enforced alongside the pinning:

1. **Version verification.** Each pinned action version was checked against its upstream repository's releases on 2026-08-12; major versions were confirmed to exist and to be the current stable major. The golangci-lint binary version (2.1.6) was verified against the official `golangci-lint-action` configuration contract.
2. **No `@main`/branch references.** Workflows pin major versions plus explicit tool binary versions; floating refs are prohibited.
3. **Fail-safe gates.** `go vet`, `go build` on linux/darwin/windows, `go test -race ./...`, `go mod tidy -diff`, linters, staticcheck, and `govulncheck` must all pass for CI to be green.
4. **Update process.** Upgrading a pinned version is a deliberate change: verify the new version upstream, run all gates locally, and record the verification in this ADR's history.

## Consequences

- Builds are reproducible and protected against upstream drift and tagged-release compromise.
- Every CI run validates the no-guessing contract mechanically: race conditions, unused code, and known CVEs in dependencies surface as hard failures.
- Overhead: workflow runs on every push/PR; negligible cost given the module size.
